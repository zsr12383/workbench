# PROMPTS

## 부트스트랩 (착수 직후)
코드는 쓰지 말고 문서만 정리해라. 승인을 기다리지 말고 바로 한다.
README 필수조건을 docs/SPEC.md에 숫자 기준으로 옮기고, 테스트·실행 명령이 있으면 AGENTS.md 빈칸에 적어라(없으면 비워 둔다).
.gitignore에 node_modules/, dist/, .env를 넣고, 지금 있는 파일 전체를 첫 커밋으로 남겨라(`git add -A`, 제공된 데이터 포함).
끝나면 커밋 해시, 내가 채울 빈칸, 모르는 것(최대 3개)만 보고하라.

## 기본 품질과 범위 밖 (SPEC 초안 때, /plan에서)
이 종류의 결과물에서 요구에 없어도 받는 사람이 '없으면 결함'으로 볼 것을 5~8개 제안하라. 항목마다 이유, 확인 방법, 비용(분)을 붙여라.
요구에 없는 '있으면 좋은 것'은 범위 밖 후보로 따로 적어라.
둘 중 어느 쪽인지 애매한 것만 나에게 물어라. 선택지 2~3개, 추천과 근거를 붙여라.
계획을 실행하면 고른 것만 SPEC의 '기본 품질'과 '범위 밖'에 넣고 커밋하라. 코드는 쓰지 않는다.

## 설계·분해 (관문 A 뒤, /plan에서)
docs/SPEC.md(성공 기준·기본 품질·제약·합격 사례), docs/research/, docs/REFERENCES.md를 근거로 구현 계획을 세워라. 구현은 하지 마라.
- research·REFERENCES: 파일마다 아직 SPEC에 없는 항목을 반영 / 무시로 나누고 이유를 한 줄씩. REFERENCES의 '결정:'과 다른 선택을 하면 이유를 적는다
- 구조: 화면·모듈·데이터 흐름을 한 단락으로, 기술 선택마다 이유와 버린 대안 하나
- 작업 목록: 첫 작업은 입력부터 결과까지 가장 얇게 끝까지 도는 판. 작업마다 완료 조건(테스트 명령), 관련 성공 기준, 예상 시간(분)
- 작업 합계(분)가 관문 C까지 남은 시간 안에 들어가게 한다. 넘치면 무엇을 뒤로 미룰지 선택지로 물어라
- SPEC의 성공 기준·기본 품질마다 연결된 작업이 있는지 확인한다. 결과 문서·README 실행 방법처럼 정리 단계에서 쓰는 것은 '정리 단계'로 표시한다
- 합격 사례와 제약(C…)을 테스트로 옮기는 작업을 넣는다
- 되돌리기 비싼 결정(구조, 데이터 모델, 의존성)만 선택지 2~3개와 추천으로 물어라

## 계획 반영 (계획이 나오면 'No, stay in Plan mode' → Shift+Tab, Default 모드에서)
방금 계획을 docs/PLAN.md 표로 옮기고 결정은 DECISIONS.md에 한 줄씩 남긴 뒤 커밋하라. 구현은 내가 작업 번호를 줄 때 시작한다.

## B 탭 시작 (곁일 세션, 새 터미널에서 `codex`)
이 세션은 곁일 세션(B)이다. AGENTS.md의 '세션 둘' 규칙을 따른다.
코드·SPEC·PLAN·DECISIONS·EXPLAIN은 고치지 말고 커밋하지 마라.
지금 할 일: <$unknowns scan | $unknowns | $review-gate | $oss-scout <필요한 것> | $explain>

## B 결과를 A에 반영 (PLAN이 생긴 뒤 새로 나온 B 결과만)
docs/research/<파일>(또는 docs/REVIEW.md)을 읽고, 현재 설계에서 바꿔야 할 것 / 추가하면 좋은 것 / 무시할 것으로 나누고 이유를 적어라.
필요하면 구조를 바꿔도 된다. 바꾸기로 한 것은 PLAN의 새 작업으로 만들고 DECISIONS에 한 줄 남겨라.

## 프로젝트 맥락 반영 (작업 1 커밋 직후, /init 대신)
AGENTS.md의 '프로젝트' 섹션과 맨 위 '테스트: … 실행: …' 줄만 채워라. 구조, 실행·테스트 명령, 주요 모듈과 책임, 외부 의존을 10줄 이내로.
다른 섹션은 고치지 마라. 끝나면 커밋하라. (B의 리뷰·점검이 이 줄에서 테스트 명령을 찾는다)

## 작업 지시 틀
[목표] 이번 작업 하나:
[맥락] docs/SPEC.md 성공 기준 N, docs/PLAN.md 작업 N
[제약] 범위 밖 파일 수정 금지, PLAN에 없는 새 의존성 금지(필요하면 먼저 물어라)
[완료 조건] <테스트 명령> 통과 + 새 테스트 2개(정상, 예외)
[서버] 오래 도는 서버는 내가 탭 1에서 띄운다. 너는 실행 명령과 포트만 알리고, 검증은 테스트로 한다.
[보고] 바꾼 파일, 실행한 명령과 결과, 남은 위험

## 반복 구현을 /goal로 (관문 B 뒤, 선택)
/goal docs/PLAN.md 작업 <N>~<M>을 하나씩 끝내라. 작업마다 AGENTS.md 순서(테스트 → 결과 → 커밋 → EXPLAIN 4줄)를 지켜라.
완료 조건: 각 작업의 완료 조건 충족, <테스트 명령> 통과, SPEC 제약 위반 없음.
멈출 조건: 작업 하나가 끝날 때마다 `date`로 시각을 확인해 <시각>(관문 C)이 지났으면, 같은 실패가 세 번 반복되면, 제약·범위를 바꿔야 하면 멈추고 보고하라.
범위 밖 작업 금지. 끝나면 내가 $spec-check로 확인한다.

## 결과 문서 (정리 단계, 기능 동결 뒤)
README가 요구한 결과 문서(예: docs/REPORT.md)를 써라. 새 기능·리팩터는 하지 않는다.
- 판단 기준과 근거: SPEC의 성공 기준·제약, DECISIONS의 결정과 버린 대안, 실무자에게 확인한 출처
- 검증 방법과 결과: 실행한 테스트 명령과 결과, 합격 사례별 결과, REVIEW에서 고친 것과 남긴 것
- 남은 한계: 미확인 항목, 범위 밖, 데이터에 대한 가정
README의 설치·실행 방법이 실제 명령과 같은지 맞추고, AGENTS.md '프로젝트' 섹션의 모듈·명령도 지금 코드에 맞게 고쳐라. 끝나면 커밋하라.

## 마무리 점검 (작업을 끝마치기 10분 전)
마무리 점검만 해라. 새 기능·리팩터 금지, 고칠 것이 보이면 목록으로만 보고하라.
1. README·요구 문서에 적힌 결과물 파일·파일명·경로가 모두 있는지 `ls`로 확인
2. `git status`가 깨끗한지, 마지막 커밋 해시. B가 쓴 docs 파일(QA-PREP.md 등)만 남았으면 그것만 커밋하고 해시를 적는다
3. README의 실행 명령 그대로 테스트를 돌린 결과, 서버가 0.0.0.0에 바인딩되는지
4. 결과 문서에 선택한 판단과 근거, 검증 결과, 남은 한계가 다 있는지(DECISIONS·EXPLAIN·REVIEW에서 모아 README가 요구한 문서에)
5. 키·토큰·개인정보가 파일에 없는지 검색
결과는 표 하나로. 그다음 내가 미리보기에서 핵심 흐름 1회, 에디터 '저장됨'을 확인한 뒤 결과물을 넘긴다.
