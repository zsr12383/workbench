목적은 사용자가 자기 작업을 짧고 정확하게 설명할 수 있게 미리 정리해 두는 것이다. 답은 짧고 구체적이어야 한다.

1. 읽는다: docs/EXPLAIN.md, docs/DECISIONS.md, docs/INTERVIEW.md, docs/REVIEW.md, docs/research/, docs/SPEC.md의 기본 품질과 범위 밖, `git log --stat`, README 필수조건, 핵심 소스 파일. 빠진 커밋 설명이 있으면, 메인 세션이면 EXPLAIN.md를 먼저 채우고, 곁일 세션이면 EXPLAIN.md는 두고 QA-PREP.md 맨 위에 '빠진 설명' 목록으로 적는다.
2. 리뷰어가 물을 만한 지점에서 질문 6개를 만든다. 질문은 결과물과 작업 기록(커밋, 문서, 대화)에서 나온다고 본다. 축마다 1~2개씩 섞는다.
   - 필수조건 X를 어디서 어떻게 만족시켰나
   - 인터뷰로 가설이 어떻게 바뀌었고, 어느 방향을 왜 골랐나
   - 기본 품질로 챙긴 것과 범위 밖으로 뺀 것, 그 경계를 어떻게 정했나
   - 대화는 짧은데 diff가 큰 커밋의 구조와 대안
   - 방향을 바꾼 지점과 확인 방법, 조사로 바뀐 설계
   - 리뷰가 찾은 문제와 어떻게 처리했나(고침, 의도됨, 미룸)
   - 외부 호출 실패나 빈 입력 같은 예외 경로, 테스트가 다루지 않는 경우
   - 조건이 바뀌면 어디를 고치나
   - 무엇을 에이전트에 맡기고 무엇을 직접 검증했나, 응답 시간을 보고 시간을 어떻게 나눴나
   - 왜 이 Codex 설정·스킬·리뷰 방식을 썼나
   - 전제가 실제 구현과 다른 질문 하나: 답은 "질문은 X를 전제하지만 실제로는 Y다"로 시작한다
3. 질문마다 답을 세 단계로 쓴다. 단계마다 1~2문장, 파일·함수·커밋 이름을 짚는다. 전체 5문장 이내, 첫 문장이 결론이다.
   - 지점: 내 코드의 어디
   - 위험·파급: 왜 문제가 되고 어디까지 번지나
   - 다음 검증·개선: 무엇으로 확인하고 어떻게 고치나
4. 핵심 함수 두 개는 입력 하나를 넣었을 때 값이 어떻게 흐르는지 3~5줄로 따라간다.
5. docs/QA-PREP.md 맨 위에 '외울 카드' 10줄을 둔다. 자료 없이 설명해야 할 때 쓴다.
   - 성공 기준의 숫자와 측정 방법
   - 핵심 파일·함수 이름 3~4개와 각각 한 줄 역할
   - 중요한 커밋 3개(해시 앞 7자리, 한 줄)
   - 고른 방향과 버린 방향 한 줄씩, 가장 큰 남은 한계 한 줄
6. 결과는 docs/QA-PREP.md에 쓰고, 사용자에게 소리 내 답해 보라고 안내한다. 첫 문장에 결론부터 말하는 연습을 시킨다.

출처: 약점 지점 → 위험·파급 → 다음 검증으로 이어지는 3단 설명 구조.
