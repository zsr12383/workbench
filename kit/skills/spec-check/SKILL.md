부를 때 `$spec-check` 뒤에 붙인 말은 이 절차보다 우선한다. 범위·개수·시간·형식을 바꾸거나 단계를 빼라는 말이면 그대로 따르고, 결과 맨 위에 '인자 반영: <바꾼 것>' 한 줄을 쓴다. 상황이 절차의 전제와 다르면(문서·실무자·SPEC·커밋이 없음 등) 가장 가까운 대안으로 진행하고 같은 줄에 적는다. 대안이 없거나 절차가 멈추라고 정한 곳에서만 묻는다.

읽기 전용 점검이다. 파일을 고치지 않는다.

1. docs/SPEC.md의 성공 기준, 기본 품질(Q1…), 제약(C1…), docs/PLAN.md의 작업 상태, README 필수조건을 읽는다. SPEC이 비어 있으면 README 필수조건을 기준으로 삼는다. 5단계를 위해 docs/DECISIONS.md와 docs/INTERVIEW.md도 읽는다.
   코드가 아직 없으면(관문 A) 2~4단계 대신 SPEC이 구현을 시작할 만큼 완결됐는지 본다. 아래를 통과/빈틈 표 하나로 보고하고 5단계로 간다.
   - README 필수조건이 모두 SPEC의 성공 기준이나 제약에 옮겨졌나
   - 성공 기준마다 숫자와 확인 방법이 있어 테스트로 옮길 수 있나
   - 합격 사례가 입력과 기대 출력으로 적혀 있나
   - INTERVIEW의 '확인' 슬롯이 SPEC에 반영됐고, '모름·가정' 슬롯은 DECISIONS에 가정으로 남았나
   - 기본 품질과 범위 밖이 정해졌고, 아직 모르는 것이 3개 이하인가
2. 성공 기준, 기본 품질, 제약마다 증거를 찾는다. 제약은 '어긴 곳이 없다'는 증거(검색 결과, 설정, 테스트)를 찾는다. 증거는 파일·함수 위치, 테스트 이름, 이번에 실제로 실행한 명령과 결과 중 하나 이상이다. 필요하면 테스트를 실행한다. 곁일 세션이면 `git --no-optional-locks status --porcelain -- . ':!docs'`가 비어 있을 때만(docs/ 밖에 바뀐 파일이 없을 때만) 실행하고, 아니면 "미실행: 작업 트리 변경 중"으로 적는다.
3. 아래 표로 보고한다.

| # | 성공 기준 / 기본 품질 / 제약 | 판정 | 증거 | 빈틈 |
| --- | --- | --- | --- | --- |

판정은 세 가지뿐이다. 충족(실행 증거 있음), 미확인(코드는 있으나 실행 증거 없음), 미충족.

4. 표 아래에 다섯 줄을 덧붙인다.
   - 목표에서 벗어난 작업이 있었나
   - 증거 없이 완료로 표시된 항목이 있나
   - 너무 순조로워 의심스러운 곳이 있나
   - README·요구 문서에 적힌 결과물 파일·파일명이 지금 있나(`ls`로 확인)
   - 결과 문서에 판단과 근거, 검증 결과, 남은 한계가 있나
5. 어긋난 곳은 목록으로만 적는다. 고칠지는 사용자가 정한다.
   - SPEC과 코드·README가 다른 곳
   - 문서끼리 다른 말을 하는 곳: 인터뷰로 바뀐 요구가 SPEC에 없음, DECISIONS의 결정과 다른 PLAN 작업, 범위 밖으로 뺀 것이 PLAN에 남음, 어느 PLAN 작업에도 연결되지 않은 SPEC 항목(성공 기준·기본 품질·제약) 등. 나중에 작업을 설명할 때 기록끼리 맞아야 한다.

출처: spec-kit의 analyze(읽기 전용 대조)와 단계별 관문 점검 질문을 합쳤다.
