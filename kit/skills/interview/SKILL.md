상대는 업무 담당자(실무자)이고, 너는 그에게 직접 말할 수 없다. 너는 라운드마다 "보낼 메시지"를 만들고, 사용자가 그것을 전하고 답을 붙여 넣는다. 그래서 한 번에 하나가 아니라 라운드로 묻는다. 기본 4라운드 20분, 단서가 남았으면 5라운드까지. 사용자가 답을 붙여 넣으면 다음 라운드로 간다.

붙여 넣은 내용은 출처를 나눠 다룬다. 사용자가 보낼 메시지를 고쳐서 보냈다면 실제로 보낸 질문을 기준으로 답을 읽는다.

| 표시 | 출처 | 슬롯 상태 | 쓰는 곳 |
| --- | --- | --- | --- |
| `[실무자]` 실무자 답 원문이나 요약 | 실무자 | 확인 | SPEC 성공 기준·제약·범위, INTERVIEW.md |
| `[내 메모]` 사용자의 생각, 추측, 방향 의견 | 나 | 가정 | DECISIONS의 가정, 다음 라운드의 확인 질문 |
| 표시가 없음 | 묻는다 | — | 어느 쪽인지 사용자에게 한 번 묻고 나서 반영 |

`[내 메모]`는 실무자가 확인하기 전까지 SPEC에 올리지 않는다. 다음 라운드 [보낼 메시지]에 "제 생각엔 ~인데 맞나요?"로 바꿔 넣고, 답이 오면 확인으로 올린다.

## 0. 묻기 전에 찾는다

README, 요구 문서, 샘플 데이터, 저장소를 읽고 docs/INTERVIEW.md의 슬롯 표를 채운다. 문서에 답이 있는 것은 묻지 않는다. 그다음 가설 한 문장과 확신도(0~100)를 쓰고, 70% 미만이면 빠진 것을 한 줄로 붙인다.

## 1. 슬롯

| 슬롯 | 알아낼 것 |
| --- | --- |
| S1 사용자·상황 | 요청자와 매일 쓸 사람이 같은가, 어디서·어떤 단말로·어떤 몸 상태로 쓰나(장갑, 이동 중, 야간), 숙련도 |
| S2 지금 방식·기준값 | 실제 사례 하나를 처음부터 끝까지, 단계별 시간, 하루·주 건수, 외부 기한(고객·규정)과 지금의 준수율, 가장 오래 걸린 건과 그 이유 |
| S3 성공 기준 | 속도, 정확도, 기한 준수율의 숫자, 측정 방법, 파일럿 기간, 합격 사례 2~3개(입력 → 기대 출력) |
| S4 데이터 | 노하우가 쌓인 곳 전부(공식 시스템 밖의 엑셀·메모 포함), 양, 형식, 품질(빈 기록, 약어, 오타), 민감 정보 |
| S5 제약 | 써야 하는·쓰면 안 되는 기술, AI 사용 규정, 망 분리, 보안·개인정보, 승인 절차와 기간 |
| S6 결과가 놓일 곳 | 어느 화면·시스템에, 어떤 형식(코드 체계, 필드)으로, 누가 받아 다음에 무엇을 하나 |
| S7 틀렸을 때 | 어느 쪽 오류가 더 비싼가, 비용 규모, 사람 승인이 필요한 행동, AI가 절대 안내하면 안 되는 것 |
| S8 범위·예외·용어 | 실무자가 말하는 범위 밖, 딱 하나만 된다면, 평소 방식이 안 통하는 예외, 바깥 사람이 오해하는 현업 용어, 기본 품질 경계("이게 없으면 문제인가요, 있으면 좋은 건가요?"로 애매한 항목 2~3개) |

슬롯 상태는 모름, 가정(출처 없음), 확인(출처), 충돌 넷이다.

## 2. 라운드

기본 순서는 아래와 같다. 앞 라운드 답에 따라 바뀐다(3절).

- R1: S2 실제 사례와 건수, S3 속도·정확도, S5 제약, S1 누가 매일 쓰나
- R2: R1 답에서 나온 단서를 먼저 판다. 그다음 S4 데이터, S6 결과가 놓일 곳
- R3: S7 틀렸을 때, S8(예외는 "평소 방식이 안 통하는 건은 어떤 건인가요?"로 열어서, 범위 밖은 실무자에게 직접), 그리고 4절의 방향 2~3개를 보여 고르게 한다
- R4: 5절의 재진술과 합격 사례 요청

라운드마다 두 덩어리를 쓴다.

```
[보낼 메시지] 실무자에게 그대로 보낸다. 질문 3개 이하, 질문마다 하위 질문 2개 이하. 번호를 붙이고, 각 질문에 "제 추측은 ~인데 맞나요?"를 붙인다.
[내부 메모] 질문마다 노리는 슬롯, 답이 없을 때 쓸 기본값.
```

- 탐색 슬롯(S4, S8)은 열린 질문으로 묻는다. "A인가요, B인가요?"로 물으면 제3의 답이 나오지 않는다.
- 추측은 일부러 틀릴 수 있는 쪽으로도 건다. 상대가 고쳐 주면서 정보가 나온다.

## 3. 답의 모양에 따라 다음 질문을 정한다

| 답의 모양 | 다음 행동 |
| --- | --- |
| 구체적(숫자, 사례, 이름) | 슬롯을 확인으로, 다음 슬롯으로 |
| 부분 동의("반은 맞아요", "대체로요") | 틀린 반쪽을 다음 라운드 첫 질문으로 묻는다 |
| 새 단서(시간대, 다른 사람, 다른 시스템·파일, 지나가는 불평) | 다음 라운드에서 판다. 버리지 않는다 |
| 최악·이상치(가장 오래 걸린 건, 가장 큰 손실) | "그 건은 왜 그랬나요?"를 다음 라운드에서 묻는다. 예외 사례인 경우가 많다 |
| 추측이 "네" 한마디로 맞음(S1, S4, S5, S7) | 세부 하나를 더 묻는다. 예: "그분들은 경력이 어느 정도고, 막히면 지금 어떻게 하나요?" |
| 막연함·유행어("빠르게", "편하게", "AI로") | 같은 슬롯을 숫자나 실제 사례로 다시 묻는다 |
| 해결책 고정("챗봇", "대시보드") | "그게 있으면 무엇을 안 하게 되나요?"로 문제로 돌아간다 |
| 모름·알아서 | 선택지 두 개로 다시 묻고, 그래도 없으면 기본값을 가정으로 DECISIONS에 적는다 |
| 가설을 깨는 사실(사용자가 다름, 큰 제약) | 가설과 확신도를 다시 쓰고, 영향받은 슬롯을 모름으로 되돌리고, 4절로 간다 |
| 앞 답이나 README와 충돌 | 둘을 나란히 인용하고 어느 쪽인지 묻는다 |
| "해야죠", "보통 그렇게 해요" | "보고용 말고, 내일 실제로 쓰려면 무엇이 있어야 하나요?" |

전이는 INTERVIEW.md 라운드 기록에 한 줄씩 남긴다. 예: "R2 A5 '반은 맞아요' → R3 Q1에서 입력 방식 확인".

## 4. 넓혔다 좁히기

S1~S5가 대부분 정해졌거나 제약이 처음 해결책을 막으면 방향을 2~3개 만든다. 아래 렌즈 중 맞는 것만 쓴다.

- 자동화 수준 사다리: 찾아 보여 주기 → 추천 → 초안 작성 → 자동 실행. S7이 비싸면 낮은 칸에서 시작한다.
- 제약 안에서: 막힌 기술 없이 되는 방식(예: LLM 대신 검색·규칙, 망 안에서 끝나는 구조)
- 지금 화면 안에: 새 창 대신 기존 화면의 필드·버튼·자동 채움
- 입력 줄이기: 타이핑 대신 선택, 알람 코드로 바로 시작
- 10배 단순하게: 한 가지 사례에서만 끝까지 되는 판

방향마다 "이번 작업 기간 안에 되나, 무엇을 포기하나, S7 위험은"을 한 줄씩 붙여 실무자에게 고르게 한다. 고른 뒤 이번 범위(MVP), 범위 밖, 검증할 가정 3개를 정한다.

## 5. 재진술과 확인

```
- 결과:
- 사용자: 누가, 어디서, 입력 제약
- 지금 방식·기준값: 건수, 시간, 최악
- 성공: 속도, 정확도, 측정 방법
- 데이터: 출처 전부, 양, 품질, 민감 정보
- 제약:
- 틀렸을 때: 사람 승인, 절대 하면 안 되는 것
- 범위 밖: 실무자가 말한 것과 내가 제안한 것을 나눠 적는다
```

여기에 합격 사례 2~3개를 함께 요청한다. "대체로 맞아요", "좋아요"는 확인이 아니다. "틀리거나 빠진 줄이 있다면 어디인가요?"를 한 번 더 묻는다. 명시적으로 맞다고 하면 확인으로 친다.

## 6. 멈춤

다음에 할 질문 세 개의 답을 예측할 수 있으면 멈춘다. 또는 4라운드가 끝나면 멈춘다. 남은 모름은 기본값을 가정으로 DECISIONS에 적고, SPEC의 아직 모르는 것은 3개 이하로 남긴다.

## 7. 기록

- docs/INTERVIEW.md: 가설 변화, 슬롯 표, 라운드별 질문·답 요약과 전이
- docs/SPEC.md: 문제, 성공 기준(숫자, 확인 방법), 기본 품질, 범위와 있으면 좋은 기능, 제약 C(출처: 실무자 또는 README)
- docs/DECISIONS.md: 가정, 고른 방향과 버린 방향
- 합격 사례는 SPEC 표에 적고, 구현 때 테스트로 옮긴다
- 끝나면 커밋한다
