부를 때 `$review-gate` 뒤에 붙인 말은 이 절차보다 우선한다. 범위·개수·시간·형식을 바꾸거나 단계를 빼라는 말이면 그대로 따르고, 결과 맨 위에 '인자 반영: <바꾼 것>' 한 줄을 쓴다. 상황이 절차의 전제와 다르면(문서·실무자·SPEC·커밋이 없음 등) 가장 가까운 대안으로 진행하고 같은 줄에 적는다. 대안이 없거나 절차가 멈추라고 정한 곳에서만 묻는다.

사용자가 이 스킬을 불렀다는 것 자체가 서브에이전트를 띄우라는 명시적 요청이다. 메인은 리뷰하지 않고, 준비·배분·취합만 한다.

곁일 세션(B 탭, 새 `codex`)에서 부르는 것을 기본으로 한다. 리뷰어가 끝날 때까지 이 세션은 막히지만, 메인 세션(A)은 계속 구현할 수 있다. 리뷰를 fork한 세션에서 돌리지 않는다. A의 대화를 물려받으면 취합이 작성자의 설명에 끌려간다.

## 1. 준비 (메인, 서브에이전트를 띄우기 전에)

1. 검토 범위를 정한다. 사용자가 범위(`<기준>..<끝>`)나 커밋 하나를 주면 그것을 쓴다(커밋 하나면 `<해시>^..<해시>`). 기준만 주면 그 해시, 아무것도 없으면 첫 커밋(제품 전체)이다. 끝을 주지 않았으면 지금의 HEAD를 `git rev-parse --short HEAD`로 고정한 해시(<끝>)다. A가 리뷰 도중 커밋해도 범위가 바뀌지 않게 끝까지 이 해시를 쓴다. `git rev-parse <기준>`이 되는지, `git diff --stat <기준>..<끝>`이 비어 있지 않은지 먼저 확인한다. 실패하면 여기서 멈추고 사용자에게 묻는다.
2. 테스트 명령을 AGENTS.md에서 찾는다. `git --no-optional-locks status --porcelain -- . ':!docs'`가 비어 있을 때만(docs/ 밖에 바뀐 파일이 없을 때만)(작업 트리가 <끝>과 같을 때만) 한 번 돌리고 결과를 메모한다. 비어 있지 않으면 A가 작업 중이니 돌리지 않고 "미실행: 작업 트리 변경 중"으로 적는다.
3. 리뷰어에게 줄 공통 입력을 정리한다. 리뷰어는 저장소를 직접 읽을 수 있으니 내용을 붙이지 말고 경로와 명령만 준다.
   - 주는 것(계약과 결과물): `docs/SPEC.md`, README 필수조건, diff 명령 `git diff <기준>..<끝>`, 바뀐 파일 목록, 테스트 명령과 결과 한 줄, AGENTS.md의 금지 목록.
   - 주지 않는 것(작성자의 추론): docs/EXPLAIN.md, docs/DECISIONS.md, 커밋 메시지 본문, 이 대화의 요약. "왜 괜찮은지"를 먼저 읽은 리뷰어는 그 설명에 끌려간다. 리뷰어가 스스로 열어 보는 것은 막지 않는다.
   - 커밋 범위는 `git log --format=%h <기준>..<끝>`의 해시만 준다.

## 2. 리뷰어 띄우기

`quick`이면 아래 A 하나만 띄운다. 아니면 A·C를 띄우고, diff가 입력 처리·인증·권한·외부 호출·셸·파일 경로 중 하나라도 건드리면 B도 함께 띄운다. 띄울 리뷰어는 한 번에 병렬로 띄운다. 토큰을 아끼기 위해 전체 리뷰는 관문마다 한 번이고, 같은 diff를 다시 돌리지 않는다. 모든 리뷰어에 공통으로:

- 부모 대화 기록을 물려주지 않는다(history `none`, fork하지 않음). 공통 입력은 프롬프트에 직접 적는다.
- 모델은 메인과 같게 둔다. 사용자가 모델을 지정했으면 그것을 쓴다.
- 프로젝트에 같은 이름의 사용자 정의 에이전트(`.codex/agents/spec-reviewer.toml` 등)가 있으면 그 agent type으로 띄운다.
- 프롬프트 첫 줄에 역할, 그다음 공통 입력, 그다음 아래 규칙을 붙인다.

| 리뷰어 | 추론 강도 | 볼 것 |
| --- | --- | --- |
| A spec-reviewer | high | SPEC 성공 기준·제약·README 필수조건과 어긋나는 동작, 빈 입력·경계값·실패한 외부 호출·동시 요청에서 깨지는 곳 |
| B security-reviewer | medium | 비밀값 하드코딩, 입력 검증 누락, 인증·권한 빈틈, 위험한 셸·SQL·HTML 처리, 로그에 남는 민감 정보 |
| C adversarial-reviewer | high | 이 코드를 깨뜨리는 구체적 입력을 만들어 보기, 테스트를 통과시키려고 테스트를 고치거나 하드코딩·mock으로 우회한 흔적, 샘플에만 맞춘 로직 |

리뷰어 규칙(프롬프트에 그대로 넣는다):

```
읽기 전용이다. 파일을 고치거나 커밋하지 말고, 다른 에이전트를 띄우지 마라.
코드는 작업 트리가 아니라 `git show <끝>:<경로>`로 읽어라. 다른 세션이 작업 트리를 고치고 있을 수 있다.
$review-agent 스킬이 있으면 그 기준과 형식을 따르고, 위 역할의 관점에 집중하라.
이번 diff가 만든 문제만 적는다. 발견마다:
[P0~P3] 제목 — 파일:줄
어떤 입력·상황에서 어떻게 실패하는지 한 문단.
실패 시나리오를 구체적으로 대지 못하면 P2 이하로 내린다.
발견이 없으면 "No findings."라고만 쓴다. 지어내지 말고, 칭찬과 요약은 쓰지 마라.
```

## 3. 취합 (메인)

1. 리뷰어 결과를 모두 받은 뒤 같은 지점을 가리키는 발견은 하나로 합친다. 서로 다른 의견은 둘 다 남긴다.
2. 발견마다 해당 줄을 `git show <끝>:<경로>`로 직접 열어 재현 가능한지 한 번 확인한다. 확인이 안 되면 "미확인"으로 표시한다.
3. 이제 docs/DECISIONS.md와 SPEC의 범위 밖 항목을 대조한다. 기록된 의도적 선택이면 지우지 말고 "의도됨: DECISIONS 근거"로 표시해 사용자가 판단하게 한다.
4. `docs/REVIEW.md`에 이번 관문 섹션을 덧붙인다.

```
## <관문> 리뷰 (<기준>..<끝>)
테스트: <명령> → <결과>
| 우선순위 | 파일:줄 | 문제 | 실패 시나리오 | 관점 | 확인 |
판정: 넘겨도 됨 / 수정 후 가능 / 불가 — 한 줄 이유
```

5. 사용자에게 표와 판정만 보여 주고, 무엇을 고칠지는 사용자가 정한다. 고치는 일은 메인 세션(A)이 PLAN의 새 작업으로 따로 한다. 곁일 세션이면 이 스킬은 docs/REVIEW.md만 쓰고 커밋하지 않는다.
